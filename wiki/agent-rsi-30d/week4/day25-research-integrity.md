# Day 25：科研评测、复现与研究诚信

能自动写实验代码的系统，也能快速制造不可复现的“阳性结果”。今天为研究代理增加独立复现、数据泄漏检查、结果一致性检查和负结果保留机制，并用 RE-Bench、MLRC-Bench、MLR-Bench 的不同评测视角审视系统能力。

## 学习目标

1. 区分工程任务成功、研究流程完成和科学结论成立。
2. 设计代理看不到、改不了的独立复现路径。
3. 检测 cherry-picking、数据泄漏、指标替换和日志伪造。
4. 用 benchmark 组合而非单一排行榜判断研究能力。

## 1. 三层评测

| 层 | 问题 | 证据 |
|---|---|---|
| 执行层 | 代码是否运行、产物是否齐全？ | 测试、日志、artifact hash |
| 研究层 | 是否提出并检验了合理假设？ | 假设卡、对照、消融、预算记录 |
| 科学层 | 结论是否可复现和外推？ | 独立重跑、hidden/transfer、误差分析 |

RE-Bench 更关注受限时间内完成研究工程任务；MLRC-Bench 强调复现与改进 ML 研究；MLR-Bench 检查端到端研究流程。它们提供互补证据，不能直接等同于“自动科学家”或 RSI。

## 2. 独立复现协议

主研究代理冻结提交后，由一个没有其对话历史的 reproduction runner 执行：

1. 仅接收代码提交、环境锁、公开数据清单和复现说明。
2. 从空缓存构建环境，不读取原运行目录。
3. 使用预先保留的新种子重跑主结果。
4. 比较逐样本输出、资源用量和主指标。
5. 将结果写入只追加的 verifier store。

复现容差要提前定义。例如准确率差异不超过 1 个百分点、运行时间不超过报告值的 1.2 倍。超过容差时，主结论标为“未复现”，不能取两次中较好的结果。

## 3. 完整性检查

建立以下自动检查：

- **数据血缘**：训练数据哈希不得包含 hidden 样本或其答案。
- **指标锁定**：主指标与聚合代码在实验前提交并冻结。
- **日志一致性**：曲线中的 step、checkpoint 和 wall time 必须单调且能对上原始事件。
- **全量汇报**：registry 中所有 run 都进入报告，包括崩溃、超时和负结果。
- **引用核查**：claim 必须能回到原文；不存在的论文、表格或数值直接判失败。

## 4. 红队故障注入

复制昨天的一个研究运行，分别注入：删除最差种子、将 dev 标签混入训练、修改主指标名称、伪造一段日志、引用不存在的实验表。蓝队只看最终仓库和 registry，尝试在 30 分钟内发现它们。每个漏检项都要转化为自动 gate。

再进行一次盲复现：复现者不查看原结果，只按 README 执行。比较原始和复现结果，并记录所有隐含依赖，例如本机缓存、未固定包版本和手工预处理。

## 5. 研究结论模板

结论按“观察 → 支持范围 → 替代解释 → 未通过检查 → 下一实验”书写。必须单列失败实验和 null result。若 hidden 提升但 transfer 下降，不能写“整体改进”，应报告具体适用范围。

## 验收标准

- 独立 runner 能从空环境复现主结果，或报告清楚、可定位的失败。
- 五类完整性攻击至少检出四类，剩余项形成新的自动检查。
- 报告包含全部种子、失败率、资源消耗和预注册主指标。
- 每个核心结论都附证据等级和适用边界。
